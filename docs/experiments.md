# Experiments Log

Durable log of things tried against open problems — what worked, what didn't, and what's currently
being tested. `docs/roadmap.md` tracks goals/status at a glance; this tracks the actual
investigation trail underneath, so dead ends don't get re-attempted blind. Newest first within each
problem section.

## Problem: make interruption (barge-in) work well

Goal-level tracking: `docs/roadmap.md` → Next → "Make interruption work well".

**Status:** gap-gated barge-in (listens only between sentences) works reliably. Continuous
mid-sentence barge-in via `NativeAec3` does not — two independent root causes found, one partially
fixed, one open. **A WebView/Chromium-based alternative is now confirmed across two independent runs
(36dB, then 41dB of real RMS suppression on this exact device) — the leading candidate, pending real
integration work** (see the three 2026-07-11 WebView rows below; attempt #1's "confirmed negative"
was itself wrong — a transient issue, caught by repeating the test rather than trusting one result).

### Currently testing / next up

- **WebView/Chromium AEC — confirmed across two independent runs (36dB, 41dB RMS suppression),
  vs `NativeAec3`'s ~0dB on this same device.** This is now the leading candidate for solving
  barge-in. Real integration plan (phased) is written up in
  `thoughts/shared/plans/2026-07-11-webview-chromium-aec-barge-in.md`.
  **Phase 0 is fully cleared, including its hardest follow-up** — both the Activity-hosted
  background-execution case and the harder Service-hosted (`WindowManager` overlay, zero Activity
  ever in front) case are confirmed working, per the two 2026-07-11 rows above.
  **Phase 1 is also done** — the real bidirectional bridge (`WebViewAecHost`) is wired into
  `VoicePipeline`'s session lifecycle behind a kill-switch, confirmed working live (9ms round trip)
  after fixing a real page-load race bug.
  **Phase 2 is also done** — real TTS render audio (short prompts and a 9.76s multi-sentence
  response) plays gaplessly through the WebView's Web Audio scheduler, confirmed glitch-free live.
  Next up: Phase 3 (capture path — `getUserMedia`-cleaned audio back to `SileroVad`) and Phase 4
  (remove the gap-gate, enable continuous listening), per the plan's phase breakdown.
- **Open bug, not yet diagnosed:** after a barge-in interrupt, the UI sometimes stays in "speaking"
  state (text visible, no audio) instead of returning to "listening." Reported 2026-07-11 — may
  overlap with the `textToSpeech` race condition fixed the same day, not yet re-confirmed live.
- **Open bug, found but not fixed:** `listenForCommand`'s STT call swallows network errors
  (`java.net.SocketException: Connection reset` seen live) identically to genuine silence, silently
  ending the conversation with no retry and no user-facing distinction.
- **Shipped, not yet AEC-related but worth tracking here:** audible state cues (`playListeningChime`/
  `playInterruptChime`) for the wall-mounted, screen-not-always-visible device; persona now told to
  keep sentences short even in long-form answers, so gap-gated barge-in gets more chances to fire
  across a long story instead of one uninterruptible block.
