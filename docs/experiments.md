## Problem: make interruption (barge-in) work well

Goal-level tracking: `docs/roadmap.md` → Next → "Make interruption work well".

**Status:** continuous mid-sentence barge-in **now ships as the default**, via WebView/Chromium's own
`getUserMedia` echo cancellation. `NativeAec3` (vendored WebRTC AEC3, never achieved real
suppression on this device) has been deleted entirely, along with every kill-switch flag — the
WebView AEC path is no longer an experiment, it's just how barge-in works now. Gap-gated barge-in
(listens only between sentences) remains as the automatic fallback if the WebView host fails to
start (e.g. missing `SYSTEM_ALERT_WINDOW`), not as a parallel maintained path.

A real regression surfaced and was fixed during this same cleanup: deleting `NativeAec3`'s
construction block also silently dropped a `wakeWordEngine.setPlatformAecEnabled(false)` call that
had been running as an incidental side effect in every prior test. Its real purpose — keeping this
device's own unreliable platform `AcousticEchoCanceler` from interfering with Chromium's separate
`getUserMedia` echo cancellation (most likely a hardware/DSP-level interaction, not something either
capture path controls directly) — had nothing to do with AEC3 itself. Without it, live testing
immediately showed a genuine self-interrupt false positive that hadn't appeared in any earlier test
this session. Restored explicitly in `startAecSession`/`endAecSession`; re-tested live and confirmed
working correctly again (user-confirmed: "it worked perfectly fine"). See the full phased trail
below (tone spike → background-execution risk → bridge scaffolding → render path → capture path →
continuous listening → drop NativeAec3 → this regression/fix) for how this was built and validated.
